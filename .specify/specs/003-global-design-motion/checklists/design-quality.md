- [x] CHK002 Are exact typography treatments specified for all ten named roles, including size, weight, line height, letter spacing, scaling behavior, and permitted font family? — Evidence: `spec.md` §Canonical type roles gives an exact ten-row family/size/line-height/weight/tracking table and 200% scaling rule; FR-013 makes it normative.
- [x] CHK003 Are exact icon size and stroke roles documented for navigation, inline, metadata, and hero contexts rather than only naming those contexts? — Evidence: `spec.md` §Canonical type roles defines metadata 16/1.75, inline 20/1.75, navigation 24/2, action 24/2, and hero 28/2.25 roles; FR-016 requires them.
- [x] CHK004 Are the approved image aspect-ratio roles enumerated for every relevant image family, including listing, gallery, profile, category, conversation, and order imagery? — Evidence: `spec.md` §Canonical image roles enumerates listing grid/rail, detail gallery, conversation/order, category/search, avatar, and Sell-composer ratios/radii; FR-025 binds display/loading/failure behavior.
- [x] CHK005 Are requirements included for root system UI, splash/launch treatment, application icon backgrounds, and other pre-route surfaces that the plan places inside the global visual migration? — Evidence: `spec.md` §Pre-route and system surfaces and FR-005 include app/adaptive icon backgrounds, splash/launch, status/navigation bars, and root surface; `plan.md` §Phase B schedules them.
- [x] CHK006 Are state requirements complete for every reusable component family, including idle, pressed, focused, selected/checked, filled, loading/busy, disabled, success, warning, and error where applicable? — Evidence: `spec.md` §Canonical component and state criteria assigns applicable states to each family; FR-017–FR-024 and `contracts/component-contracts.md` define observable state behavior and non-applicable boundaries.
- [x] CHK007 Are requirements defined for every shared cross-route surface named in scope—primary navigation, overlays, sheets, toasts, skeletons, image failures, empty states, and errors? — Evidence: `spec.md` §Included screen families, §Canonical component and state criteria, and FR-025–FR-034 cover every named surface; `contracts/component-contracts.md` defines their behavior.
- [x] CHK008 Does the migration scope explicitly require the route inventory to be refreshed at implementation start so routes added after specification are not omitted? — Evidence: `spec.md` FR-005 and §Verification sampling require refresh before migration and final verification; `contracts/migration-evidence-contract.md` §Inventory rule repeats both checkpoints; T061 performs the final re-scan/diff and blocks omitted evidence.

## Requirement Clarity

- [x] CHK009 Is “approximately 90% white/neutral, 8% black, and 2% semantic accent” defined with a reviewable sampling or measurement method and a clear meaning for “ordinary use”? — Evidence: `spec.md` §Canonical visual language defines a 10x10 resting-screen grid, exclusions, classification, and 85–95/5–12/≤3 aggregate bands; T027 predeclares the samples and T028 executes/calculates them without discretionary substitution.
- [x] CHK010 Are “premium,” “quiet,” “subtle,” “restrained,” “comfortable,” “prominent,” and “minimal” translated into objective component or review criteria wherever they govern acceptance? — Evidence: `spec.md` §Canonical component and state criteria explicitly maps each term to measurable geometry, contrast, shadow, density, duration, and motion restrictions.
- [x] CHK011 Is the boundary between permissible centrally derived tonal variants and a prohibited second/accent palette explicit enough to classify every derived color consistently? — Evidence: `spec.md` §Canonical visual language permits only enumerated derived state/overlay/skeleton surfaces from canonical roles, bans an independent accent palette, and requires a `CENTRAL_DERIVATION` or exception classification under FR-056.
- [x] CHK012 Is the meaning of “essential,” “non-essential,” and “lowest-priority readable metadata” explicit enough to determine when muted `#9A9A9A` is permitted under the contrast baseline? — Evidence: `spec.md` §Canonical visual language eliminates the ambiguous readable-muted case: all readable text/placeholders use contrast-qualified roles, `#9A9A9A` is limited to non-readable decoration/non-essential disabled treatment, and FR-018 requires `textSecondary` for disabled button labels.
- [x] CHK013 Are “ordinary layout,” “documented space-constrained composition,” and valid full-bleed exceptions defined tightly enough to distinguish a justified raw geometry value from design drift? — Evidence: `spec.md` §Canonical spatial and shape language defines ordinary layout, full bleed, geometry exceptions, required DesignException fields, and scale-bound gutters; FR-007/FR-011 govern exceptions.
- [x] CHK014 Are button, selection, sheet, modal, card, and favorite spring roles specified with measurable physical constraints beyond “restrained” and “avoid exaggerated bounce”? — Evidence: `spec.md` §Canonical motion language and `contracts/motion-contract.md` §Canonical springs give exact mass/stiffness/damping/clamping plus settle/cancellation/oscillation acceptance constraints.
- [x] CHK015 Is “important confirmation” distinguished from ordinary completion well enough to make the allowed haptic events exhaustive and non-overlapping? — Evidence: `spec.md` §Canonical motion language enumerates every allowed event, defines high-consequence as irreversible or externally visible persisted change, and lists excluded contexts; FR-041 is exhaustive.
- [x] CHK016 Is the distinction between a short static collection and a “long content collection” defined with data-size or growth criteria that determine when long-list requirements apply? — Evidence: `spec.md` §Responsive, accessibility, and performance baseline defines long content as remote-backed and not contractually capped below 20 rows or growing across sessions; FR-045 requires virtualization and a 30-real-row runtime criterion; T052 consumes the inventory and requires evidence for every exclusion.

## Requirement Consistency

- [x] CHK017 Are the palette semantics consistent between the color table, button rules, component contract, and plan—especially the separate meanings of primary text and inverse text? — Evidence: `spec.md` §Canonical visual language uses `textPrimary #111111`, `textInverse #FFFFFF`, and readable disabled-label `textSecondary #717171`; §Canonical component criteria, FR-018, and `contracts/component-contracts.md` §Button use the same meanings.
- [x] CHK018 Does the permitted use of success, warning, and other semantic colors align with the Constitution’s statement that color is reserved for genuine signal and error by default? — Evidence: Constitution Principle VI reserves color for genuine signals; `spec.md` §Canonical visual language and FR-009/FR-010 restrict success/warning/error to real state and prohibit decorative accent use.
- [x] CHK019 Are the requested fixed palette values consistent with the WCAG 2.2 AA baseline, including explicit role/surface restrictions wherever an exact color cannot meet the applicable threshold? — Evidence: `spec.md` §Canonical visual language records exact role values and WCAG thresholds, disallows `#9A9A9A` for readable content, and supplies contrast-qualified text roles; FR-008 and `plan.md` §Summary agree.
- [x] CHK020 Are reduced-motion requirements consistent across component feedback, navigation, onboarding, skeletons, sheets, and the edge case where the platform setting changes while the application is active? — Evidence: `spec.md` §Canonical motion language and FR-042/FR-043 define the same immediate-endpoint/≤120 ms opacity policy for all families and live setting changes; `contracts/motion-contract.md` applies it per interaction.
- [x] CHK021 Are the route-preservation requirements consistent with the visible Explore-to-Browse relabeling so no requirement implies creation of a new `/browse` business destination? — Evidence: `spec.md` §Included screen families and FR-040 retain the existing `/explore` destination; `contracts/component-contracts.md` §Navigation explicitly forbids adding a route merely for relabeling.
- [x] CHK022 Are the scope exclusions and migration requirements consistent about checkout and orders—allowing presentation migration while forbidding changes to their business behavior and payment architecture? — Evidence: `spec.md` §Excluded changes, §Migration sequence table, and FR-053/FR-054 permit presentation coverage while preserving Stripe/webhook/order authority; `plan.md` Constitution Check IV agrees.
